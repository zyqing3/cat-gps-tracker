# GNSS 最低功耗配置实测报告

**测试日期**：2026-10-15 ~ 10-16
**硬件**：LilyGO T-SIM7670G-S3-Standard（ESP32-S3 + SIM7670G-MNGV，模组固件 V1.9.05），USB COM7，室内窗边，原装 GNSS 天线
**固件**：`firmware/at_bridge`（AT 直通桥），**全程只发 GNSS 相关 AT，不发网络/PDP/HTTP、不做上传**
**脚本**：`scripts/gnss_power_test.py`
**原始数据**：`logs/gnss_power_20261016_001113.json/.csv`（24 次主矩阵）、`logs/gnss_power_rerun9.json/.csv`（补测 3 次）

---

## 一句话结论

**推荐「全四系（`AT+CGNSSMODE=15`）+ 上电默认启动（不要发 `AT+CGPSCOLD`）」**：定位最快（中位 **26 秒**，范围 20–31 秒）、3/3 次全部拿到真定位、能耗 0.088 mAh，是唯一"又快又能稳定定上位"的配置。

反过来，**「仅 GPS」在本机位置 6 次全部 180 秒超时、一次都没定上位**，白耗 0.370 mAh 还换不到一个坐标——**省下的那点电流，远远赔不起搜星时间的损失**。

---

## 一、为什么这么测：没有电流表也能比功耗

板子还没买电流表，但这件事其实不需要电流表也能测清楚，因为：

```
功耗（mAh） = 电流（mA） × GNSS 开着的时间（小时）
```

- **电流**是已知量：查规格书就有（见第五节，约 7～12 mA）。
- **时间**可以精确测：模组开着 GNSS 到"定上位"花了多少秒，串口读得出来。

所以本次实验的**核心指标就是「GNSS 开启时长」**——同一档星座的电流差别很小（最多差一倍以内），但不同配置的搜星时间能差好几倍。**把时间压下来，比拼那几毫安更有效。**

> 一句话给猫咪项圈：GNSS 每多开 1 秒，就多耗一点电；定得越快，越省电。

## 二、测试方法

### 2.1 用例矩阵

两个变量交叉，共 8 格，每格重复 3 次：

| 变量 | 取值 |
|---|---|
| **A. 星座组合**（`AT+CGNSSMODE`） | 仅 GPS(1) ／ GPS+北斗(9) ／ GPS+Galileo(5) ／ 全四系(15) |
| **B. 启动方式** | 上电默认（`CGNSSPWR=1` 后直接轮询）／ 显式冷启动（`AT+CGPSCOLD`） |

mode 取值来自手册 21.2.7（`AT+CGNSSMODE=?` 实测返回 `(1,3,5,9,13,15)`）。

### 2.2 每格流程

```
关 GNSS（CGSETV=1,0 + CGNSSPWR=0）→ 等 5 秒冷却
 → 开天线电源（CGDRT=1,1 + CGSETV=1,1）→ CGNSSPWR=1（等 READY!）
 → 等 2 秒初始化 → 设星座组合 AT+CGNSSMODE=<mode>
 →（冷启动格）AT+CGPSCOLD
 → 记 T0 → 每秒 AT+CGNSSINFO 轮询 → mode=2/3（且通过体检）即为定位，记 TTFF
 →180 秒仍不定位记 timeout → 关 GNSS → 下一格
```

**轮转顺序**：第 1 轮跑完所有 8 格，再跑第 2 轮、第 3 轮。卫星几何随时间变化，轮转能把"时间段偏差"平摊到每个配置上，比"一个配置连测 3 次"公平得多。

### 2.3 三个关键判定

1. **TTFF** = 设好星座（或冷启动）到定上位的秒数。
2. **GNSS 开启时长** = `CGNSSPWR=1` 到定上位的秒数（**含上电初始化那几秒**，这才是真正费电的窗口，也是算能耗用的口径）。
3. **真定位体检**：模组偶尔会报"假定位"——mode 明明是 2/3，但卫星数空、日期空。这种数据服务器会拒收，所以按主固件 `stepWaitFix` 的同款标准判定：**必须看得到卫星 + 日期是合理的 ddmmyy**，否则不认，继续等。

| 星座组合 | 启动方式 | 定位成功 | 假定位 | 超时 | TTFF 中位 | TTFF 范围 | GNSS 开启中位 | 卫星数中位 | 估算能耗 |
|---|---|---|---|---|---|---|---|---|---|
| 仅 GPS | default | 0/3 | 0 | 3 | — | — | — | — | 白耗 0.370 mAh（无位置） |
| 仅 GPS | cold | 0/3 | 0 | 3 | — | — | — | — | 白耗 0.370 mAh（无位置） |
| GPS+Galileo | default | 1/3 | 0 | 2 | 65 s | 65 s | 69 s | 16 | 0.192 mAh |
| GPS+Galileo | cold | 1/3 | 0 | 2 | 72 s | 72 s | 77 s | 14 | 0.216 mAh |
| GPS+北斗 | default | 5/6 | 1 | 0 | **31 s** | 24–94 s | 34 s | 23 | **0.084 mAh** |
| GPS+北斗 | cold | 3/3 | 0 | 0 | 58 s | 58–62 s | 63 s | 30 | 0.153 mAh |

| 全四系 | cold | 3/3 | 0 | 0 | 54 s | 35–63 s | 59 s | 29 | 0.178 mAh |

（GNSS 开启中位 = 能耗计算口径；估算能耗用第六节的电流。）

### 3.2 逐次 TTFF 明细（方便看波动）

| 配置 | 每次 TTFF（秒） | 每次 GNSS 开启（秒） |
|---|---|---|
| 全四系 / default | 26, 20, 31 | 29, 24, 34 |
| 全四系 / cold | 63, 35, 54 | 68, 39, 59 |
| GPS+北斗 / default | 94, 31, 29, 36, 24 | 98, 34, 33, 40, 27 |
| GPS+北斗 / cold | 58, 62, 58 | 63, 66, 63 |
| GPS+Galileo / default | 65（另 2 次超时） | 69 |
| GPS+Galileo / cold | 72（另 2 次超时） | 77 |
| 仅 GPS / 两种启动 | 6 次全超时 | 6 次都白开 180 s |

### 3.3 三个直接读出来的规律

**① 星座开得太少，反而更费电。**
仅 GPS 6 次全部 180 秒超时。它每次白耗 `180 s × 7.4 mA = 0.370 mAh`——是"全四系"成功定位（0.088 mAh）的 **4.2 倍**，而且**连一个坐标都没拿到**。在项圈场景里，"定不上位"比"定得慢"严重得多：App 上看不到猫，电也白花了。

**② 星座不是越多越好，但"少到 GPS+Galileo"这种组合最尴尬。**
GPS+Galileo 只成功 1/3，成功时也要 65–72 秒。相比之下 GPS+北斗 6/6、全四系 6/6。

**③ 不要发 `AT+CGPSCOLD`（显式冷启动）——它只会更慢。**
三组里"上电默认"都**不慢于**冷启动：全四系 26 s vs 54 s（快一倍），GPS+北斗 31 s vs 58 s，GPS+Galileo 65 s vs 72 s。
原因也说得通：`CGNSSPWR=1` 之后引擎**自己就已经开始搜星了**，我们等 2 秒再设星座、再发 `CGPSCOLD`，等于把这 2 秒的搜星进度**清零重来**。白扔的进度，就是白扔的电。

## 四、推荐配置与依据

### 推荐：`AT+CGNSSMODE=15`（全四系）+ 上电默认，**不发** `CGPSCOLD`

推荐的操作顺序：

```
AT+CGDRT=1,1      # 天线电源 GPIO 设成输出
AT+CGSETV=1,1     # 天线供电
AT+CGNSSPWR=1     # GNSS 上电（等 +CGNSSPWR: READY!）
AT+CGNSSMODE=15   # 全四系
（直接开始轮询 AT+CGNSSINFO，不要发 CGPSCOLD）
```

**依据：**

1. **最快**：TTFF 中位 26 秒，是全部成功配置里最快的。
2. **最稳**：3/3 真定位、0 假定位、0 超时；TTFF 范围 20–31 秒，是所有配置里**波动最小**的（GPS+北斗 是 24–94 秒，波动大得多）。
3. **能耗并列最低**：全四系/default 0.088 mAh，GPS+北斗/default 0.084 mAh，两者只差 5%——**在电流假设的误差范围之内，分不出胜负**（见第六节敏感性分析）。既然能耗打平，就用**更稳更快的那个**。
4. **卫星数最多**：中位 32 颗（典型构成 GPS ~15 + 北斗 ~13 + GLONASS ~3），定位质量更有保障。

> 小观察：全四系模式下 Galileo 的卫星数经常报 0（3 次里 2 次为 0，另一次单独测到 6）。以手册字段顺序解读，mode=15 实际上多数时候按"GPS + 北斗 + GLONASS"三系在工作。这不影响结论（该配置依然最快最稳），但如果将来想省掉一个星座，**GLONASS 或 Galileo 都是候选**，北斗建议保留——它贡献的卫星数最多（~13）。

### 淘汰说明

- **仅 GPS**：0/6 成功，直接淘汰。
- **GPS+Galileo**：只有 1/3 成功，且成功也要 65 s 以上，比全四系慢 2.5 倍。
- **GPS+北斗**：能耗与全四系打平，但出现 1 次假定位、TTFF 波动大（24–94 s），可靠性不如全四系。可作为**备选**（电流略低，若将来电流表实测确认其真的比全四系省电，可以换它）。

## 五、电流假设与误差说明（重要，请连误差一起看）

### 5.1 电流值从哪来

`docs/reference/SIM7670_Series_Spec_231205.pdf` 里**没有** GNSS 电流表（只有 LTE 的 4.2 mA 空闲 / 800 uA 睡眠）。GNSS 电流来自**同族的 SIM7672X 硬件设计手册** `docs/reference/SIM7672X_Series_Hardware_Design_V1.02.pdf` 的 **表 56**（Standalone GNSS current consumption，VBAT=3.8V，CAT1 关闭）：

| 手册场景 | 典型电流 |
|---|---|
| GPS(L1) tracking | 7.40 / 7.32 mA |
| GPS(L1)+GLONASS cold start | 9.79 / 9.69 mA |
| GPS(L1)+BEIDOU tracking | 8.73 / 8.71 mA |
| GPS(L1)+BEIDOU cold start | 11.09 / 9.88 mA |
| GPS(L1)+GALILEO+BEIDOU tracking | 10.31 / 10.14 mA |
| GPS(L1)+GALILEO+BEIDOU cold start | 10.60 / 10.89 mA |
| 同上，搜星/捕获场景 | 9.85 ～ 12.41 mA |

本报告采用的取值（取"更贴近本实验场景"的那一档）：

| 星座 | 采用电流 | 来源 |
|---|---|---|
| 仅 GPS (1) | 7.4 mA | tracking |
| GPS+Galileo (5) | 10.0 mA | **手册无此行，按相邻配置内插——估计值** |
| GPS+北斗 (9) | 8.7 mA | tracking |
| 全四系 (15) | 10.7 mA | cold start |

### 5.2 误差有多大

1. **型号差异**：表 56 是 SIM7672X，本板是 SIM7670G。同族但非同一型号，**按 ±2 mA 看待**。
2. **场景差异**：表里 tracking / cold start / 失锁 / 搜星混排，对应关系不是一一对应。本实验每格都是断电重搜（相当于 cold start），所以优先取 cold start 值。
3. **天线 LNA 未计入**：表 56 是 GNSS 芯片本身的电流。本板用有源天线（GPIO 1 供电），LNA 那部分电流没算进来。**实际值应略高于表中值**。
4. **只算了 GNSS，没算整机**：ESP32-S3 主控、模组待机等功耗不在本次范围（本次只解决"GNSS 怎么配最省"）。

### 5.3 敏感性分析：换个电流假设，结论会不会翻？

因为电流是估的，所以额外用**统一 10 mA**再算一遍（这样完全不用相信手册的分档）：

| 星座 / 启动 | 手册电流 | 能耗（手册电流） | 能耗（统一 10 mA） |
|---|---|---|---|
| GPS+北斗 / default | 8.7 mA | 0.084 mAh | 0.097 mAh |
| **全四系 / default** | 10.7 mA | 0.088 mAh | **0.082 mAh** |
| GPS+北斗 / cold | 8.7 mA | 0.153 mAh | 0.176 mAh |
| 全四系 / cold | 10.7 mA | 0.178 mAh | 0.166 mAh |
| GPS+Galileo / default | 10.0 mA | 0.192 mAh | 0.192 mAh |
| GPS+Galileo / cold | 10.0 mA | 0.216 mAh | 0.216 mAh |

**结论**：前两名（全四系/default 与 GPS+北斗/default）在两种假设下互有胜负、差距都在 ~15% 以内，属于**打平**。**其余排名完全不变**——"仅 GPS 最差、冷启动更慢"这两个结论极其稳健，不受电流假设影响。

> 也就是说：**推荐全四系，主要理由是"快 + 稳"；能耗上它和 GPS+北斗并列第一。**

## 六、关于热启动：为什么没测

**决定：不测（`AT+CGPSHOT` 不纳入本次矩阵）。** 理由：

1. **物理上就没有"热"的条件**。本矩阵每格结束都会关 GNSS（`CGSETV=1,0`+`CGNSSPWR=0`），而**GNSS 一断电星历就没了**——每个格子本质上都是冷启动，根本不存在"热"的状态可测。
2. **已实测会毒害引擎**。项目此前验证过：星历为空时发 `AT+CGPSHOT`，引擎会拿着坏星历乱搜，**120 秒一颗星都看不到**。硬测等于故意制造一组无效数据。
3. **真正有意义的测法**（"GNSS 一直开着电、刚定位完再热启动"）与项圈实际用法不符——项圈为了省电必然要关 GNSS。

脚本里仍保留了 `--starts hot` 选项，将来若要专门验证这个坑可以手动跑。

### 补充：还想测但本次没做的

- **"GNSS 开启后到第一颗可见星"的时间**：`AT+CGNSSINFO` 在未定位时只回一串空字段（实测 `+CGNSSINFO: ,,,,,,,,`），看不到卫星数。要看这个过程得开 NMEA（GSV 语句）或 GNSS 测试模式，但那样会**污染 AT 口**——桥是按"静默 300ms"判定回应结束的，NMEA 持续刷屏会让每条命令都拖满 5 秒，反而破坏正在测的时序。故本次跳过。

## 七、顺带发现并修掉的 4 个坑

测试过程本身踩到几个坑，都已修好并写进代码注释：

1. **桥固件的 DTR 被 `gpio_hold` 锁死（本次最关键的修复）**
   主固件入睡前会 `gpio_hold_en(DTR)` + `gpio_deep_sleep_hold_en()` 把 DTR 锁在高电平（让模组睡觉）。这个锁存在 RTC 域里，**跨软件复位保留**——`esptool` 烧录后的 RTS 复位也清不掉。桥原来只做 `digitalWrite(DTR, LOW)`，被 hold 压住完全无效，模组被 DTR 高电平按在睡眠态，**AT 全部无回应**。
   修复：`at_bridge.ino` 的 `setup()` 先 `gpio_hold_dis()` + `gpio_deep_sleep_hold_dis()` 再拉低 DTR。

2. **`AT+CGSETV` 前必须先 `AT+CGDRT`**
   手册 9.2.11：GPIO 方向必须先由 `CGDRT` 设成输出，否则 `CGSETV` 直接回 `ERROR`。原脚本关天线时先发 `CGSETV=1,0` → ERROR → 天线其实没断掉。已改为先 `CGDRT=1,1`。

3. **`+CGNSSINFO` 的卫星字段顺序：手册与 TinyGSM 注释矛盾**
   - 手册 21.2.21：`GPS, GLONASS, GALILEO, BEIDOU`
   - TinyGSM `TinyGsmClientSIM7672.h` 注释：`GPS, BEIDOU, GLONASS, GALILEO`

   **实测判据**：mode=9（GPS+北斗）时只有第 1、第 4 个字段有数；mode=5（GPS+Galileo）时只有第 1、第 3 个字段有数。**这正好对应手册顺序**（北斗在第 4 位、Galileo 在第 3 位），故采信手册。若按 TinyGSM 注释解析，mode=9 会被误读成"GPS+Galileo"。

4. **"假定位"真的会出现**
   主矩阵 24 次里出现 1 次：mode 报 3、TTFF 只有 26 秒，但卫星字段和日期**全是空的**。已加体检逻辑剔除（与主固件 `stepWaitFix` 同款标准），并对该格补测了 3 次。

## 八、本次测试的局限

1. **没有电流表**：能耗是"实测时间 × 手册电流"的估算，不是直接测出来的。误差主要来自电流假设（±2 mA / ~±20%），而非时间（时间误差只有 ~2 秒，因为轮询周期约 2 秒）。
2. **单一地点、单一时间段**：室内窗边，全部测试集中在约 1 小时内完成。换个开阔地、换个时段，**绝对 TTFF 会变**；但"全四系比仅 GPS 快且稳"这个**相对结论**预期仍然成立。
3. **样本量小**：每格 3 次（GPS+北斗/default 5 次）。TTFF 本身波动大，中位数只代表一个粗略水平。
4. **GNSS 引擎行为依赖模组固件版本**（V1.9.05），换固件需重测。

## 九、后续建议

1. **买电流表后复测一次**：用实测电流替换手册值，把本报告的能耗列换成真值，顺便验证有源天线 LNA 的额外功耗。
2. **把 `AT+CGNSSMODE=15` 固化进主固件**（实际上主固件已经是 `GNSS_MODE_GPS_GLONASS_GALILEO_BDS`，与本次结论一致）。
3. **去掉任何 `CGPSCOLD`/`CGPSHOT` 调用**——本次实测两者都是负收益。
4. 若将来"定不上位就放弃"的策略需要调，注意**仅 GPS 在窗边会 100% 失败**，超时设得再长也没用。

## 十、复现方法

```bash
# 1. 烧 AT 直通桥（注意：别改烧录参数）
bash scripts/flash.sh firmware/at_bridge COM7

# 2. 快速冒烟（8 格各 1 次，约 15 分钟）
python scripts/gnss_power_test.py --reps 1

# 3. 完整矩阵（8 格 × 3 次，约 50 分钟）
python scripts/gnss_power_test.py

# 4. 只测某几种组合
python scripts/gnss_power_test.py --modes 1,9,5,15 --starts default,cold --reps 3
```

结果写入 `logs/gnss_power_<时间戳>.json` / `.csv` 并打印汇总表。任意一格 180 秒超时记为 timeout 并继续；Ctrl+C 会先关 GNSS 再释放串口。
